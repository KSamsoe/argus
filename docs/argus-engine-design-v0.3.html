Argus Engine

A general-purpose 2D game engine whose primary user interface is a protocol. The editor, the CLI, the test runner, and the coding agent are all clients of the same daemon — and the human and the agent tune the game on the same world, at the same time.

§0Thesis

Every mainstream engine treats the editor as the ground truth and the world as something you look at through it. That is why bolting an agent onto Unity or Godot stays shaky: the agent is a translator standing between a language model and a system that was never meant to be driven blind. State lives in serialized objects that only exist properly on the main thread, scene files are ten-thousand-line dumps of GUID references, and a script change nukes the world.

Argus inverts the ordering. The engine is a long-running daemon that owns a world; a small JSON-RPC protocol is the only way to read or change that world; the editor is one client among several. The simulation is deterministic and time-controllable, so any run is a reproducible artifact. Scenes are queried, not read. And because the human and the agent share the same world through the same protocol, the things agents are bad at — game feel, timing, juice — become collaborative: the human's hands on the sliders produce data the agent can act on.

The target is general-purpose 2D: action, platformer, grid-based, and simulation games should all come out of the same engine without one of them fighting it. The internals are data-oriented — an archetype ECS, structure-of-arrays storage, a Rust core with Luau for game logic — because that is what makes the world flat, legible, and fast to snapshot, not because any one genre demands it. Three-dimensional rendering, networking, and cross-platform determinism are explicitly deferred.

To keep the design honest about generality, four reference games are threaded through the document and gate the build plan (§18). Each stresses a different axis, and the engine is done when all four feel native.

Reference gameGenreWhat it stresses
SwarmBullet heavenContinuous time, tens of thousands of runtime entities, hot-path systems, few authored entities
DelveGrid roguelikeDiscrete time, procedural generation, turn order, seed sweeps, mostly text and state
HollowPlatformer / metroidvaniaGame feel, kinematic physics, tilemaps, camera, rooms and streaming, thousands of authored entities
OutpostColony simulationMany interacting systems, pathfinding and jobs, data tables, sim speed control, hours-long sessions, save games, balance tuning
Design goal, one sentence

An agent, starting from an empty directory and a one-paragraph brief, can build, run, test, and iterate on a playable prototype of any of the four reference games without a human clicking anything — and a human can then sit down, play it, mark what feels wrong, and hand the agent a reproducible replay of every mark.

§1Principles

Five rules. Every later decision should be traceable to at least one of them; when two conflict, the earlier one wins.

P1

The daemon is the truth; everything else is a client.

There is no button that isn't also a command. The editor cannot do anything the CLI can't, because it has no other way to reach the world.

P2

Query, don't read.

No client ever needs the whole scene in memory. Every response is a summary by default, paginated, with drill-down on request. Token budget is a first-class resource.

P3

Deterministic and time-controllable.

Fixed timestep, seeded RNG, recorded input. Scene + seed + input log + code version reproduces any run exactly. Step, pause, snapshot, seek, replay are engine primitives, not tooling.

P4

Flat data, visible side effects.

Components are plain data. Systems declare what they read and write. Nothing lives in script globals. There is no hidden state for the agent to be surprised by.

P5

One world, two hands.

Human and agent edit the same world through the same transactions. Feel is tuned by hand, but the hand's movements are logged, replayable data.

§2Architecture

Three tiers: a Rust core process (argusd), a protocol boundary, and a set of clients. The core is a single process that hosts the ECS world, the fixed-step simulation, the renderer, audio, the asset importer, and the Luau VM. Clients connect over a local socket (Unix domain socket or Windows named pipe) or over stdio when embedded.

Process model

One daemon per project. The daemon holds exactly one world and a stack of snapshots. There is no separate edit mode and play mode with different data representations: "editing" is the world with the simulation stages disabled; "playing" is the world with them enabled. Entering play takes a snapshot; stopping restores it. Because the snapshot is a memcpy of SoA columns, the transition costs single-digit milliseconds even at Swarm's entity counts, and there is nothing to desync. For Outpost, where a session is hours long and the world is the save game, the same mechanism is what "save" and "load" are built on (§6).

The renderer is optional at daemon start (argusd --headless). Headless mode still supports semantic observation (§8) and can render to an offscreen texture on demand for screenshots, using the same wgpu path with a software adapter in CI.

Isolation: a script or plugin fault must not take the daemon down. Luau systems run sandboxed inside the daemon with instruction budgets. Rust plugin systems are loaded as dynamic libraries; a panic in one is caught at the system boundary, the system is disabled, and the fault is reported through the protocol as an event. The world remains intact and inspectable — which is exactly when the agent most needs to inspect it.

Decision

Single process, single world, snapshots instead of modes. Multiple concurrent play sessions (for A/B comparison, §10) are implemented as forked worlds from a snapshot inside the same daemon, not as extra processes.

Rationale: P1 and P3. The alternative — an edit-time scene graph and a run-time world — is the root of every "play mode changed my scene" bug and doubles the surface the agent has to reason about.

§3Data model

Argus is an archetype ECS. Entities are IDs; components are plain data structs stored column-wise (structure-of-arrays) per archetype; systems are functions that run over queries. Swarm needs this for performance, but it is the right choice for every reference game because of what it does for an agent: the whole game state is a set of flat tables, every field is greppable, and there is no inheritance hierarchy hiding behavior three files away. Delve's turn state, Hollow's room contents, and Outpost's colonists and stockpiles are all the same kind of thing — rows in typed columns.

Entities

An entity ID is a 64-bit value (index + generation). Authored entities — the ones a human or agent places in a scene file — additionally carry a stable string id such as player or door.east, unique within the scene and stable across sessions, saves, and renames of everything else. Runtime-spawned entities (bullets, generated dungeon rooms, colonists born mid-game) never get string ids and are never written to scene files. This split, authored versus runtime, drives the storage design in §4. The proportion varies enormously by genre — Swarm has a dozen authored entities and fifty thousand runtime ones, Hollow has thousands authored and few runtime, Outpost's runtime state is the game and must persist as a save — and §4 and §6 are written to handle all three shapes.

Transform hierarchy is first-class: a Parent component gives an entity a local transform relative to another, propagated in a dedicated stage before present. Characters with attached weapons, UI trees, and Outpost's buildings with sub-parts all use it; Swarm's bullets simply don't have the component and pay nothing.

Components

A component is a schema plus a column. Schemas are declared once and introspectable everywhere: from Rust via derive, or from Luau via a schema file. Every field has a type, a default, an optional range, and a doc string. The doc string is not decoration: it is what argus describe returns, and therefore what the agent reads.

components/hitstop.luau — component schema declared from script
return component "HitStop" {
  doc    = "Freezes an entity's simulation for N frames after a hit. Read by sim.hitstop.",
  frames = field.u8 { default = 0, range = {0, 30}, doc = "Remaining frozen frames" },
  scale  = field.f32{ default = 0.0, range = {0, 1}, tune = true,
                      doc = "Time scale while frozen. 0 = full stop" },
}

The tune = true flag marks a field as a feel parameter. It changes nothing at runtime; it tells the editor to expose the field in the tuning panel and tells the recorder to log changes to it (§10). Hot fields — anything touched every frame by thousands of entities — should be declared in Rust so they get a native SoA column with no VM boundary; cold, game-rule fields can live in Luau schemas. The protocol does not distinguish between the two.

Systems and stages

Systems run in a fixed order of stages: input → sim → late → hierarchy → present. The sim stage runs on the game clock (§6) and is the only stage that may mutate gameplay state; present runs at render rate and is read-only (interpolation, camera, UI). Each system declares the components it reads and writes. The scheduler uses this for parallelism, but more importantly the agent uses it to answer "what could have changed Health?" with a single query instead of a grep.

systems/hitstop.luau — a script system
return system "sim.hitstop" {
  stage  = "sim",
  after  = { "sim.damage" },
  reads  = { "HitStop" },
  writes = { "HitStop", "TimeScale" },
  run = function(q)
    for e, hs, ts in q:each("HitStop", "TimeScale") do
      if hs.frames > 0 then
        hs.frames -= 1
        ts.value = hs.scale
      else
        ts.value = 1
      end
    end
  end,
}

Tags are zero-size components. Relations (parent/child, "owned by") are components holding entity references, and the engine keeps them valid across despawn by nulling dangling refs at frame end and emitting an event, so nothing crashes on a stale handle and the agent can see that it happened.

Prefabs and overrides

A prefab is a named bundle of components with values, and may itself be built from another prefab (door/locked from door/base). An entity that references a prefab stores only the fields it overrides; everything else is inherited at load and re-inherited when the prefab changes. The rules are deliberately few, because override models are where scene formats go to die:

  • Inheritance is per field, never per component. Overriding Door.locked does not detach the rest of Door.
  • Adding a component the prefab lacks is an override; removing one the prefab has is an explicit -Component entry, so a reader sees the removal in the file.
  • A prefab may contain child entities (a door with a frame and a light); children are addressed by path (@door.east/light) and overridden the same way.
  • world.get {entity, resolved: false} returns only the overrides; resolved: true returns the merged result with each field's provenance (own, door/locked, door/base). The editor's inspector shows the same provenance as a colour.
  • Changing a prefab is a transaction like any other; the index lists every instance, and the change feed reports how many entities the change touched.
Decision

Archetype ECS with SoA columns, declared read/write sets, and authored-versus-runtime entity distinction as a first-class concept.

Rationale: P2 and P4. Declared side effects turn "why did this change" from an investigation into a query.

§4Project & scene storage

Files are the source of truth and are designed to be read by git, by humans, and by agents in that order of priority. The daemon builds a queryable index from them; the index is a cache and is never committed.

project layout
mygame/
  argus.toml              # project: name, clock config, plugin list, default scene
  components/             # Luau component schemas, one per file
  systems/                # Luau systems, one per file, name = path
  defs/                   # game data tables: items, recipes, jobs, enemies (see below)
    items.toml
    recipes.toml
  prefabs/
    enemy/bat.toml
    door/locked.toml
  scenes/
    arena/                # a flat scene: one directory
      scene.toml          # scene metadata: bounds, enabled system groups, seed policy, clock
      player.toml         # one authored entity per file, filename = string id
      spawner.north.toml
    hollow/               # a large scene: subdivided into rooms
      scene.toml          # room graph, streaming radius, transitions
      rooms/
        cavern-03/
          room.toml       # bounds, tileset, neighbors
          door.east.toml
          save-point.toml
          tiles.map.toml  # index for a binary chunk (see below)
        cavern-04/ …
  assets/                 # source art, audio, fonts; importer watches this tree
  tests/                  # scenario tests (§9)
  plugins/                # optional Rust crates compiled to dylibs
  .argus/                 # index.db, import cache, snapshots, marks — gitignored

Entity files

One authored entity per TOML file. Small, flat, diffable, and there is never a reason to read a neighbor's file to understand this one.

scenes/hollow/rooms/cavern-03/door.east.toml
prefab = "door/locked"
tags   = ["door"]

[Transform]
pos = [46.0, 8.0]

[Door]
leads_to = "@cavern-04/door.west"   # entity ref by string id, room-qualified
key      = "item:key.brass"         # def ref, not a GUID
locked   = true

Rooms and streaming

A scene is either flat (one directory of entities, the Swarm and Delve case) or subdivided into rooms (the Hollow case, and Outpost's map chunks). Rooms are directories; the scene file holds the room graph. The daemon streams rooms in and out around the player by graph distance, so a two-hundred-room game never has more than a handful of rooms live, and the index still answers queries about rooms that aren't loaded. Transitions between rooms are an engine event with a hook for the game (fade, camera slide), not something each game reinvents.

Data tables

Much of a game's authored content isn't entities at all: item definitions, crafting recipes, job priorities, enemy stat blocks, dialogue lines. These live in defs/ as TOML tables with declared schemas, referenced as item:key.brass, indexed and queryable like everything else (world.defs {table: "recipes", where: {output: "item:bread"}}). Outpost is mostly defs; an agent balancing its economy edits tables and runs seed sweeps, never touching a scene.

Asset and prefab references are paths. Renames are performed through the protocol (asset.move), which rewrites references and appends to .argus/moves.log so an out-of-date client can catch up. This trades GUID robustness against filesystem renames for legibility; a rename done outside the tool leaves a clear "missing reference" error with the old path in it, which is fixable by an agent in one command. That trade is deliberate.

Bulk authored data

Some authored content is legitimately large: a tilemap, a placed-prop layer with thousands of entries, a baked navigation grid. These get a text index file plus a binary chunk: the index carries everything a reader needs to reason about the data (dimensions, tileset, layer names, a content hash), and the chunk carries the numbers. The agent reads the index and queries the chunk through the protocol (scene.tiles.get {rect}); it never sees a 40,000-line array.

The index

On load and on every file change, the daemon updates .argus/index.db (SQLite): entities by scene, components by entity, references between assets, prefabs, and entities, plus a full-text column over doc strings. Every world.* and scene.* query in §5 is served from this index when the world is not loaded, and from the live world when it is, with identical result shapes. The agent does not need to know which.

Decision

File-per-entity TOML for authored content, rooms as directories with streaming, data tables in defs/, binary chunks with text indexes for bulk data, path references not GUIDs, SQLite index as cache only.

Rationale: P2 above all. A room directory of forty 20-line files is something an agent can hold in its head; one 8,000-line YAML file is not, and git can't merge it either. The index is what keeps this true at Hollow's scale, where the whole scene is thousands of files.

Open

TOML versus KDL. TOML is universally known and every model has strong priors for it; KDL nests better for deep component data. Leaning TOML because prior strength matters more than elegance for this audience.

§5Protocol

JSON-RPC 2.0 over a local socket, with server-initiated notifications for subscriptions. JSON rather than a binary format because the primary client is a language model and the secondary client is a human at a terminal; the hot paths (frame streaming, snapshot transfer) use out-of-band shared memory or a sidecar binary channel that the JSON message merely points at.

The method set is small on purpose. Ten namespaces, roughly fifty methods, mirrored one-to-one by CLI subcommands and MCP tools.

Profiling as a query

The scheduler already times every system every tick; prof.* just exposes it. prof.systems {last: 600} returns per-system mean and p95 in stage order; prof.worst {n: 5} returns the five slowest recent ticks with a per-system breakdown and the entity counts by archetype at that tick; prof.alloc counts allocations by system so a Luau system that builds a table per entity is visible; prof.capture {ticks: 300} writes a Tracy-compatible trace for the human. This is what makes the §17 targets something the agent can enforce rather than something a human notices: a perf regression is a query result with a system name on it.

Undo is the change feed

Every committed transaction records its inverse. Undo and redo are edit.undo and edit.redo, scoped per author, so the human's Ctrl+Z in the editor never unwinds the agent's work and vice versa. Because the feed is shared, both parties can also see what the other undid.

Access

The local socket is owned by the user account that started the daemon and needs no further authentication. Any remote access — the tablet review client in §11, or a teammate's editor — goes through a token issued by argus token with a scope (observe, review, edit) and an expiry, over TLS. Nothing in the player runtime (§15) listens on any socket at all.

Shape of a query

request
{ "method": "world.query", "params": {
    "select": ["id", "Transform.pos", "Health.cur"],
    "where":  { "has": ["Enemy"], "within": { "of": "@player", "r": 6.0 } },
    "order":  "dist(@player)",
    "limit":  5 } }

response
{ "result": {
    "frame": 812,
    "total": 31,
    "rows": [
      ["e:4011", [3.2, 1.1], 4],
      ["e:4018", [-2.9, 2.0], 4],
      ["e:3990", [4.4, -3.7], 2],
      ["e:4102", [-5.1, 0.3], 4],
      ["e:4077", [1.0, 5.8], 1] ],
    "truncated": true, "next": "c:9f2" } }

Every read method obeys the same contract: a default limit of 50, a total that is always present so the agent knows what it isn't seeing, a cursor for continuation, and a compact row-array encoding rather than repeated keys. The design target is that any default response fits in about 2 KB. world.summary — entity counts by archetype, named entities and their key fields, active systems, current frame and seed — is the one-screen orientation call and is what the MCP shim runs automatically on connect.

Shape of an edit

{ "method": "edit.begin",  "params": { "author": "agent:claude", "note": "tighten north spawner" } }
{ "method": "edit.set",    "params": { "entity": "@spawner.north", "path": "WaveSpawner.interval_s", "value": 0.28 } }
{ "method": "edit.commit" }
// → writes scenes/arena/spawner.north.toml, appends to the change feed, emits edit.committed

Edits to authored entities write files on commit. Edits to runtime entities are live-only. A transaction is atomic and carries an author tag, so the change feed — the log every client can subscribe to — always answers "who changed this and why". edit.lock lets an author (typically the human) fence a set of entities or paths; a write into a locked path fails with an error that names the lock and its owner.

Errors are documentation

{ "error": {
    "code": 4102,
    "message": "WaveSpawner.interval_s must be in range [0.05, 10]; got 0.0",
    "hint":    "Use 0.05 for the fastest legal spawn rate, or set per_wave higher instead.",
    "ref":     "components/wave_spawner.luau:14" } }

Every error carries a human sentence, a hint written as if to a capable colleague, and a file:line reference. This is the cheapest lever in the whole design: an agent that gets a good error message rarely needs to read a doc.

Decision

JSON-RPC, small fixed method set, summary-first responses with totals and cursors, transactional edits with author tags, structured errors with hints.

Rationale: P1, P2, P5. The protocol is the product; everything else is a view of it.

§6Determinism & time

A run is a value. Given the same scene, seed, input log, and code version, the world at tick N is bit-identical. This is what makes every other feature in the document possible: tests that don't flake, marks that reproduce, A/B comparisons that mean something.

Two clocks

The single biggest way an action-game engine overfits is by making a fixed timer the only way time moves. Argus has a clock abstraction with two drivers, and every scene declares which one drives its sim stage.

continuous
The sim advances at a fixed rate (60 Hz default) whether or not anything happened. Rendering is decoupled and interpolates between the last two sim states. Swarm and Hollow live here.
discrete
The sim advances only when a command is issued: sim.advance {by: "turn"}, or the game calling clock.advance() after the player acts. Between advances nothing simulates; present still runs for animation and UI. Delve lives here, and so does any puzzle, card, or tactics game.

The two are the same thing to the replay system. A continuous run's input log records inputs by tick; a discrete run's log records commands by turn. Seek, fork, marks, and tests work identically. A game can mix them: a tactics game runs discrete for the turn structure and continuous for the animations that play between turns, with the continuous stage gated on "a turn is resolving". The scheduler lets a system group bind to either clock.

Speed is a property of the continuous clock: sim.speed {x: 3} runs three sim ticks per render frame, and {x: 0} is pause. Outpost's 1×/3×/10× controls and the human's "let the colony run for a night" are this one call; the agent uses the same call to fast-forward a balance test, headless, at whatever rate the CPU allows. Wall-clock time is never visible to gameplay code; sim.time is tick count times the timestep, on whichever clock is driving.

Randomness

Randomness comes from named streams. Each system that wants randomness declares a stream name and gets a PCG32 seeded from hash(run_seed, stream_name). Adding or reordering a system therefore does not perturb the random sequence any other system sees, which is the property that keeps a replay valid across small code changes.

Floating point is f32 with the usual determinism caveats: reproducible on the same platform and build, not guaranteed across compilers or CPUs. Cross-platform bit-determinism (fixed-point math, or a constrained float subset) is a known path and an explicit non-goal for v1, since the human and the agent are almost always on the same machine.

Snapshots, seek, fork

A snapshot is a serialization of every SoA column plus the RNG states, the event queue, and the Luau heap. Because columns are contiguous, a snapshot at 100k entities is a few tens of megabytes and takes low single-digit milliseconds. In development the daemon keeps a ring of keyframe snapshots (every 60 frames by default, configurable) plus the full input log, so sim.seek {frame: 740} is "restore the nearest earlier keyframe, replay inputs forward" and completes in well under a second for any point in the last several minutes of play.

sim.fork creates a second world from a snapshot inside the same daemon. Forks get their own tick counter and can be stepped independently, which is how the harness runs "same inputs, two code versions" and how the editor offers live A/B toggling (§10).

Long sessions change the ring's shape but not its mechanism. An Outpost session is hours long; keeping a keyframe every second would be gigabytes. The ring thins with age — every second for the last minute, every minute for the last hour, every ten minutes beyond — so a mark from three hours ago still reproduces, just with a longer replay from its nearest keyframe.

a run identity, as the recorder stores it
run     = { scene = "outpost/valley", seed = 0x5EED_2026, code = "git:a41f2c9+dirty",
            clock = "continuous@60", inputs = ".argus/runs/2026-09-10T14-02/input.log" }

Save games

A save is a snapshot with a schema version, written by sim.save to a player-facing location instead of the dev ring. The difference from a dev snapshot is that it must survive code changes: components carry a version, and a component's schema file may declare a migrate function from older versions. On sim.load the daemon runs migrations column by column and reports each one as an event, so an agent can see "Health migrated v2→v3 for 1,204 entities" and a test can assert a saved game from last month still loads. Outpost is the reference game for this; Delve uses it for run persistence; Swarm barely needs it and pays nothing.

Decision

Two clock drivers behind one replay model, named PCG streams, same-platform f32 determinism, age-thinned keyframe ring + input log for seek, forked worlds for comparison, versioned snapshots as save games.

Rationale: P3. Every collaboration feature in §10 is a thin layer over seek and fork, and the clock abstraction is what keeps that true for discrete games.

§7Scripting & hot reload

Game logic is Luau. It is fast for an interpreted language, sandboxed by design, gradually typed so schemas can be checked before a run, and small enough that an agent's priors about Lua transfer cleanly. Hot-path systems — bullet integration, collision broadphase, particle update, Outpost's pathfinding and flow fields — are Rust, either in the engine or in a project plugin crate, and are compiled to a dynamic library the daemon loads.

The reload story is the same for both: because all state lives in components (P4), swapping code never loses state. For Luau, script.reload recompiles the changed files, rebinds system functions, and continues from the current frame; the daemon freezes script globals after module load so nothing can accidentally live there. For Rust plugins, the daemon snapshots, unloads the old dylib, loads the new one, restores, and continues. The agent sees a compile error as a structured script.errors response with file:line and the compiler's message, never as a crash.

Two rules the engine enforces rather than recommends: a system may only touch components it declared, and a system may not hold references across frames. Violations are errors at load time where they can be detected statically and at run time otherwise. Both exist to keep the side-effect declarations honest, which is what makes world.who_writes trustworthy.

Decision

Luau for rules, Rust for hot paths, both hot-reloadable because state is never in code.

Rationale: P4. Unity's domain reload is the single largest tax on agent iteration in existing engines; this design makes it structurally impossible to need one.

Open

Whether to expose a C# path via NativeAOT for teams with existing code. Not in v1; the cost is a second binding layer and a second set of docs.

§8Observation

The agent's senses are layered from cheapest to most expensive, and the protocol makes the cheap ones easier to reach than the expensive ones. Pixels are the last resort, not the first.

L0 ~300 B
Summary. world.summary: counts, named entities, frame, seed, active systems. Answers "where am I".
L1 ~2 KB
Query. world.query with selection, filters, spatial predicates, aggregates. Answers "what is the state".
L2 stream
Events. obs.events / obs.subscribe: structured log of spawn, despawn, damage, death, collision, sound played, system errors, edits. Answers "what happened".
L3 ~1 KB
Diff. obs.diff {since: frame}: which entities appeared, vanished, or changed which fields, with counts. Answers "what changed since I last looked".
L4 ~3 KB
Semantic frame. obs.frame {format: "semantic"}: camera rect, every visible entity with screen-space bounds, HUD text, active screen-space effects. Answers "what does the player see" without an image.
L5 image
Pixels. obs.frame {format: "png"}, optionally annotate: true to overlay entity ids and bounds so the agent can ground what it sees to what it can query. Answers "how does it look".

The layering pays off differently per genre. For Swarm the agent lives at L1 and L3. For Delve, which is mostly state and text, L4 is nearly the whole game: the semantic frame carries the map, the log, and the menus, and pixels are rarely needed. For Outpost the agent leans on L2 and aggregates — world.query with group_by and sum over stockpiles, job queues, and colonist needs — because the question is "is the economy drifting", not "where is entity 4011". The semantic frame is game-extensible through a Describe component so that a HUD, a dialogue box, or a colony overview panel can say what matters about itself.

Audio is observed as events, not waveforms: "played sfx/hit_heavy at frame 812, gain 0.8, on entity e:4011". A clip export exists for the human (§10), but the agent reasons about sound as a log.

Two derived helpers earn their place. obs.trace {entity, frames} returns one entity's component history over a window, which is the tool for "why did the player die at 812". And obs.why {event} walks the declared write sets backwards from an event to list the systems that could have caused it, in stage order — a static answer, but usually enough to point the agent at the right file.

§9Test harness

A test is a scenario: load a scene, fix a seed, script some input, run some frames, assert on state and events. It runs headless in the daemon, takes tens of milliseconds for a short scenario, and never flakes, because §6.

tests/wave_clear.luau
return scenario "first wave clears within 20s" {
  scene = "arena", seed = 7,
  run = function(t)
    t.input:hold("move", {1, 0}, frames = 60)      -- walk right for a second
    t.input:tap("fire")
    t:run_until { event = "wave.cleared", max_frames = 1200 }
    t.expect:count({ has = {"Enemy"} }):eq(0)
    t.expect:field("@player", "Health.cur"):gte(1)
    t.expect:events("damage", { target = "@player" }):count():lte(3)
    t.expect:snapshot("wave1_end", { select = {"Transform.pos", "Health.cur"}, where = { has = {"Player"} } })
    t.expect:perf("sim"):p95_ms():lt(4.0)
  end,
}

The same harness on the discrete clock, and at simulation scale:

tests/delve_stairs.luau — a discrete-clock scenario
return scenario "stairs are always reachable on floor 1" {
  scene = "delve", seeds = range(1, 200),
  run = function(t)
    t:advance { by = "turn", n = 1 }                  -- generate floor
    t.expect:path("@player", { has = {"Stairs"} }):exists()
    t.expect:count({ has = {"Monster"}, within = { of = "@player", r = 3 } }):eq(0)
  end,
}

tests/outpost_food.luau — a balance scenario, fast-forwarded headless
return scenario "a 6-colonist start does not starve in 30 days" {
  scene = "outpost/valley", seeds = range(1, 20),
  run = function(t)
    t:run_until { sim_time = days(30), speed = "max" }
    t.expect:sum("Stockpile.food"):gte(60)
    t.expect:events("colonist.died", { cause = "starvation" }):count():eq(0)
    t.expect:series("Stockpile.food", every = days(1)):trend():gte(0)
  end,
}

Golden snapshots are of selected state, not images: the expectation names the components and filter, the harness stores a compact JSON, and a failure prints a field-level diff. Image goldens exist as an opt-in for rendering work, with a perceptual threshold, and are expected to be rare.

The runner (argus test) supports the things an agent actually reaches for: run one test by name, run with a seed sweep (--seeds 1..50) to shake out order-dependent bugs, run a failing test and dump a replay file the human can open in the editor, and export a short clip of the failing window so the human can see it without reproducing it. Output is a compact text report by default and JSON with --json. Everything runs identically in CI with the software render adapter.

Performance assertions run against the headless sim and are stable enough to gate on because the sim is deterministic; only the wall-clock envelope varies, and the assertion is on a percentile with a generous default margin.

Decision

Scenario tests in Luau, state goldens by default, seed sweeps, replay and clip export on failure.

Rationale: P3 makes this cheap; P2 shapes the output. The point is that the agent's edit-test loop is seconds, not minutes, and never needs a human to press play.

§10Human–agent collaboration

This is the section the rest of the document exists to support. Agents are strong at what is legible: logic, structure, tests, refactors, tedious placement. Humans are strong at what is felt: hit-stop length, screen-shake curves, how a dodge reads, whether a death is satisfying. A serious engine has to make the handoff between those two cheap in both directions, and the mechanism is the same throughout: the human's actions are recorded as structured, replayable data on the shared world, and the agent's proposals are things the human can feel rather than read.

Marks

While playing, the human presses one key (F8 by default) to drop a mark. A mark captures the frame, a snapshot, the last five seconds of input, a two-second clip rendered from the ring, and an optional one-line note spoken or typed afterward ("dash feels late"). Marks land in .argus/marks/ and surface to the agent as a queue: each is a fully reproducible bug report. The agent runs sim.seek to the mark's frame, traces the relevant entities, and proposes a change — without ever asking "what were you doing when it happened?".

Tuning sessions

Any field with tune = true appears in the editor's tuning panel as a slider while the game runs. Every movement of every slider is logged with its frame: "human set HitStop.scale 0.0→0.15 at frame 3011, →0.08 at 3090, →0.1 at 3140". The agent subscribes to this stream and sees not just the final value but the search path, which carries information ("they tried higher, backed off"). When the human ends the session, the final values are committed as an ordinary transaction with the human as author, and the agent can be asked to propagate the same feel to related parameters, write the test that pins it, or explain what the value does in the doc string.

Tuning is not only about feel. In Outpost the tune fields are job priorities, consumption rates, and growth curves, and the human's slider is a hypothesis about balance rather than a judgement about weight. The loop is the same: the human nudges a value while watching the colony at 10×, the agent sees the path, and then does what a human can't — runs the twenty-seed, thirty-day sweep from §9 against each candidate value and reports which ones starve. Feel is tuned by hand; balance is tuned by hand and verified by machine.

Proposals and A/B by feel

The agent can submit a transaction as a proposal rather than a commit. The editor shows pending proposals; the human plays with F9 toggling between the current world and a fork with the proposal applied, at the same replay point, with the same inputs. Three variants of a screen-shake curve become three forks and one key to cycle them. The human picks by feel, in seconds, and the pick is the commit. Nothing about this requires the human to read a diff.

Review requests

The reverse channel: the agent asks for judgement. obs.review {clip, question} queues a short clip and a question ("does the enemy death read as a kill?") to the editor; the human answers with one keystroke or a sentence. The queue is visible in the editor's agent panel and drains at the human's pace. Because the clip is rendered from a deterministic replay, the agent can attach the exact frame range and the human can scrub it.

Locks and the change feed

The human can lock any entity, component, or path ("camera feel is mine"). The agent's write fails with the owner's name and note. Both parties see one change feed, author-tagged, so the human returning after an hour can read what the agent did as a sequence of notes, and the agent resuming after the human's session can read the human's tuning log the same way.

Agent does well here

  • Build systems, components, prefabs, and tests from a brief
  • Reproduce and diagnose marks from replay
  • Place and wire authored entities; bulk edits
  • Propagate a tuned value across related parameters
  • Refactor while tests pin behavior
  • Seed sweeps, perf triage, dead-code hunts

Human does well here

  • Judge timing, weight, readability, satisfaction
  • Tune with a slider while playing
  • Choose between proposals by feel
  • Answer "does this read?" in one keystroke
  • Decide what the game is about
  • Lock what shouldn't be touched
Decision

Marks, tuning logs, proposals-as-forks, review requests, locks, one change feed. All built from seek, fork, and author-tagged transactions.

Rationale: P5. The engine's job is not to make the agent good at feel; it is to make the human's feel cheap to express and impossible to lose.

§11Editor

The editor is a separate process that speaks only the protocol. This is a constraint, not a convenience: if the editor ever needs a private channel to the daemon, the protocol is missing something the agent also needs. The first editor is immediate-mode (egui) for build speed and because its panels map naturally onto protocol calls: the hierarchy is world.query, the inspector is world.describe plus edit.set, the viewport subscribes to frames, the timeline scrubber is sim.seek over the keyframe ring.

Two panels exist only because of §10: the tuning panel and the agent panel (pending proposals, review requests, marks, the change feed). And one toggle exists to teach: "show as command" prints the CLI equivalent of every action the human takes, so the human learns the agent's language by using the editor and can paste a command into a chat instead of describing a click.

Open

Whether a browser-based editor (the daemon serving a web UI) should replace egui later. It would make the editor reachable from a tablet during a playtest, which is attractive for review requests. Not a v1 concern.

§122D subsystems

A general 2D engine is mostly the sum of subsystems that any one genre would skip. Each of these is built into the core, exposed through the protocol like everything else, and costs nothing for a game that doesn't attach the relevant components. The reference game that drives each one is named so the design has a concrete customer.

Physics, in tiers

Three tiers, chosen per entity, sharing one broadphase (a spatial hash over the live world, rebuilt incrementally each tick). Overlap: shapes that report contacts and nothing else — Swarm's bullets, Delve's triggers, Outpost's zones. Kinematic: a character controller that moves a shape against a tilemap and other kinematic bodies with slopes, one-way platforms, moving platforms, step-up, and the timing affordances that platformers live on (coyote time, jump buffering, corner correction) as tunable fields rather than something every game reimplements — Hollow. Dynamic: real rigid bodies with joints, from an optional Rapier module for the games that need a physics toy, not a default. The kinematic tier is the one worth getting exactly right, because it is where platformer feel comes from and it is the tier the agent can least judge by itself.

Tilemaps

Layers of tiles over a grid, with auto-tiling rules declared in TOML, collision derived from tile properties, and chunked storage (§4). Editable through the protocol at the rect level, so an agent can carve a room without touching pixels and a human can paint in the editor and both land in the same chunk. Hollow and Outpost.

Camera

Follow with dead zones, lookahead, room bounds, smoothing, and shake as a first-class component with a curve and a decay, all of them tune fields. Cameras are entities; cutting between two is an event. Hollow's rooms and Outpost's free pan-and-zoom are two configurations of the same component.

UI and text

A retained UI tree built from the same entities and hierarchy as everything else, with a flexbox-style layout system, bitmap and SDF text with shaping, nine-slice panels, and input focus. Not a separate world: a menu is a query away like anything else, and the semantic frame (§8) reads it directly. Delve's menus, Outpost's inspector panels and overview screens, and every game's pause menu. This is the subsystem that most clearly separates a general engine from an action-game framework, and it is scheduled early for that reason.

Dialogue and localization

Dialogue as a def table (§4) with a small node graph — lines, choices, conditions on world state, effects as edits — runnable from Luau and inspectable through world.defs. All player-facing strings go through a string table keyed by id; the agent can author in one language and a translator can fill the others without opening the engine.

Pathfinding and jobs

A navigation grid derived from the tilemap and blocking entities, with A* for individuals and flow fields for crowds, both Rust hot-path systems. On top of it a job system: entities publish tasks with requirements, agents claim them by priority and distance. Outpost is the customer, but Delve's monsters and any game with NPCs use the same path queries, and obs.why can explain "why is this colonist idle" from the job system's declared events.

Lighting

2D lighting as a render pass — point and cone lights, occluders derived from tiles and sprites, normal-mapped sprites optional — off by default and zero-cost when off. Hollow's caverns; Outpost's day-night cycle.

Input actions

Gameplay never sees keys. An action map in input.toml declares actions (move, jump, confirm) with bindings per device and per player slot, so two gamepads are two players from the start. The input log (§6) records actions, not device events: a replay survives a rebind, a test written against a keyboard runs against a gamepad, and the agent's input.inject says {action: "jump"} rather than naming a scancode. Rebinding at runtime is a UI over the same table. Delve's menus, Hollow's controller feel, and couch co-op in any of them.

Accessibility

Mostly consequences of decisions already made, stated so they get built. Rebinding comes with the action map; text scaling and high-contrast palettes are UI theme tokens; input-hold and toggle alternatives are action-map options; and the semantic frame (§8) is, without modification, a screen-reader feed — the same call the agent uses to know what's on screen can drive a player's narrator. A colour-blind simulation post pass (§13) lets the agent and the human check readability without guessing.

§13Animation, VFX, and audio

These three are where feel lives and where the previous draft was thinnest. They follow the same rule as everything else — text-authored, queryable, tunable, observable as events — because these are precisely the systems the tuning sessions of §10 need to reach.

Sprite animation

An Animator component runs a state machine declared in TOML: states reference clips, transitions have conditions on component fields (Velocity.y < 0 → fall) and blend windows, and every state can carry events by frame: the frame the foot lands fires sfx/step, the frame the sword is out enables the hitbox, the frame the enemy's eyes flash is the telegraph. Events are ordinary engine events, so the agent sees "hitbox enabled at frame 4 of slash" in the log and a test can assert it. Clip rates, anticipation frame counts, and hold frames are tune fields; a human adjusting a wind-up while playing is the canonical tuning session. Aseprite tags import directly as clips. Skeletal 2D via a Spine-compatible runtime is a phase-5 module; the state machine and events are the same either way.

Tweens and sequencing

A tween is a component: target path, from, to, duration, easing curve, on-complete event. Squash-and-stretch, UI slides, and camera nudges are all tweens, and because they are data the agent can query what is currently animating and the replay reproduces them exactly. Above tweens sits a timeline: a def table of tracks (tweens, animator states, camera cuts, dialogue lines, events) against time, playable from Luau, scrubbable in the editor. Cutscenes, boss intros, and Outpost's event vignettes are timelines, which also answers the open question about coroutine state: sequencing lives in data, not in the Luau heap.

Particles and VFX

An Emitter component: shape, rate or burst, lifetime, and curves over lifetime for velocity, size, colour, and rotation, all as TOML with the curves as control-point lists. Particles are not entities; each emitter owns an SoA pool updated by a Rust system and drawn instanced, so Swarm's fifty thousand sparks cost nothing to the ECS. Screen-space effects live in a post stack: an ordered list of passes (flash, palette swap, chromatic aberration, vignette, CRT, colour-blind simulation) that a game enables with parameters, every one a tune field. The hit-flash-plus-hit-stop-plus-shake combination that makes an impact feel heavy is three tunable systems the human can adjust together in one session.

Materials and shaders

Sprites reference a material; a material is a WGSL shader plus parameters, declared in a sidecar with typed uniforms. The engine ships a small library (lit, unlit, palette, dissolve, outline) and a game adds its own as text. Shader authoring is a natural agent task — WGSL is code, compile errors come back through script.errors with line numbers, and the annotated screenshot path lets the agent check the result. Materials hot-reload like everything else.

Audio

The mixer has named buses (music, sfx, ui, ambience) with a routing tree, ducking rules declared as data ("dialogue ducks music by 6 dB over 200 ms"), and 2D spatialization by distance from the listener entity. Sound events carry variation sets (pick one of five footsteps, pitch-jitter ±5%) so the game asks for sfx/step and the mixer chooses. The music system is adaptive by design: a track is a set of layers with a tempo, transitions between tracks happen on beat or bar boundaries, and intensity is a parameter a system writes (Music.intensity = enemies_near / 10). Hollow's room-to-room music and Outpost's day-night ambience are both this. All of it is observable as the event log in §8; the human hears it, the agent reads it.

Decision

Animation state machines with frame events, tweens and timelines as data, emitter pools outside the ECS, a post stack of tunable passes, text materials, and a bus-and-layer audio model.

Rationale: P4 and P5. Feel is the thing the human tunes; every knob it needs must be a field the tuning panel can show and the recorder can log.

§14Assets

Source assets live in assets/ and are described by sidecar TOML files that the agent can write: a sprite sheet's frames and pivots, an animation's clip list and rates, an audio file's gain and variation set. The importer watches the tree, produces a cache in .argus/, and reports every import as an event with warnings ("frame 7 is empty", "texture not power-of-two, padding"). Aseprite and Tiled files import natively with their internal structure exposed through the sidecar.

Generated art — from an image model or a text-to-sprite pipeline — drops into the same tree and gets the same treatment. The agent can author a placeholder sprite as a described shape (kind = "rect", size = [8, 8], color = "#E8703F") so gameplay work never waits on art, and the human replaces the file later without touching a reference.

§15Shipping

Everything before this section describes a development environment. A game is finished when a player who has never heard of a daemon can double-click it, and the engine has to make that path as deliberate as the agent's path.

The player runtime

A release build is the same core with the protocol server compiled out, the editor and index absent, Luau precompiled to bytecode, and assets packed. There is no socket, no .argus/ directory, and no way to attach; the dev-only surface is a Cargo feature, not a runtime flag, so it cannot be turned on in the field. argus build --release --target windows produces a single directory — executable, one asset pack per language, and a save location per platform convention.

Two dev-side features survive into release on purpose. The recorder stays, in a bounded form: the last thirty seconds of actions and a keyframe, so that a player pressing a report key or hitting a crash produces a replay file the team can open with sim.seek. A player bug report becomes a mark. And save migrations stay, because they are how a patched game loads an old save.

Targets

Windows, macOS, and Linux from day one, since wgpu and the input stack already cover them. The web target (wasm + WebGPU, with a WebGL2 fallback) is not a stretch goal; it is how most 2D games get playtested, and a shareable link is the cheapest way to get a human's feel onto a build the agent made. Mobile is a later target with no design blockers beyond input and UI scale. Consoles are out of scope.

Assets and content

A release pack is built from the import cache, not the source tree: compressed textures in atlases, audio in the platform's preferred codec, defs and scenes in a binary form of the same schema. Packs are content-addressed so a patch ships only changed chunks. Localization packs are separate so a language can be added without a rebuild.

Platform services

A platform plugin interface — achievements, cloud saves, rich presence, input glyphs, overlay — with a Steam implementation first and a null implementation for everything else, so game code calls one API and tests run without Steam present.

Modding

Argus is a modding platform whether or not that is intended: the daemon, the Luau sandbox, and defs/ are exactly what a modding system needs. The decision is to intend it. A release build can load mod packs — additional defs, scenes, assets, and Luau systems — from a user directory, in a declared load order, with the same sandbox and instruction budgets as the game's own scripts and the same schema validation. Doing this from the start costs a load-order rule and a namespace prefix on mod content; retrofitting it costs a rewrite of asset loading. Games that don't want mods set one flag.

Networking, preserved

Multiplayer stays out of v1, but the sim is kept honest for it. Determinism plus an action log is most of a lockstep model; snapshots plus resimulation is most of rollback. The v1 rule that preserves both: nothing in the sim stage may read from a device, the wall clock, or a local-player singleton — inputs arrive only as per-player-slot actions through the input log. That rule already holds for replays, so the cost is a lint, not a feature.

Decision

Protocol compiled out of release builds, bounded recorder kept in, desktop and web targets from the start, content-addressed packs, a platform plugin with Steam first, modding intended, networking preserved by a sim-stage rule.

Rationale: a serious engine is judged by what reaches players. The choices here are the ones that are cheap now and unaffordable later.

§16Agent packaging

argus mcp starts a stdio MCP server that exposes the protocol as a small tool set — on the order of a dozen tools, not a hundred: summary, query, describe, edit, run, seek, observe, events, test, reload, marks, propose. Each tool's description is generated from the same schema the CLI help uses. The CLI (argus) mirrors the tool set exactly, so an agent that prefers a shell loses nothing and a human reading the agent's transcript can rerun any call.

argus docs --for-agent emits an ARGUS.md from the live daemon: the component schemas with doc strings, the system list with stages and write sets, the prefab catalog, and the current scene summaries. It is regenerated on demand, so it never drifts from the project, and it is what a coding agent's project-level instructions should point at. The engine's own reference documentation ships in the same shape.

Decision

One schema generates the protocol, the CLI help, the MCP tool descriptions, and the agent-facing docs.

Rationale: P1. Four surfaces that can drift is how integrations become "shaky at best".

§18Build plan

Six phases. Each gate is phrased as something the agent can do with one or more of the reference games, because the agent is the user whose experience is being designed and the four games are the proof of generality. No renderer until phase 1, on purpose: if the protocol-and-sim loop isn't compelling headless, a renderer will only hide that. Two of the four games are chosen to be complete without a renderer for exactly that reason.

Phase 0~7 weeks

ECS core with SoA columns, archetypes, and hierarchy; scheduler with stages, declared write sets, and both clock drivers; Luau binding with component and def schemas; JSON-RPC daemon with session, world, edit, sim (play, pause, step, advance, speed, run_until), script; TOML scenes, rooms, defs, and prefab overrides; SQLite index; action maps with the action log; prof.*; CLI; scenario test runner with state goldens and seed sweeps. No renderer, no audio, no input devices — actions are injected only.

GateFrom an empty directory and a paragraph brief each, an agent using only the CLI builds headless cores of Swarm (continuous clock, 50k entities, waves) and Delve (discrete clock, generated floors, turn order) with passing tests, and can answer "why did the player die" in both from events and traces. If either game fights the protocol, that finding is the phase's output.

Phase 1~8 weeks

wgpu sprite renderer with instancing and atlases; windowed and offscreen modes; keyboard, mouse, gamepad input with recording; audio mixer with event log; asset importer with sidecars and watch; tilemaps with chunks and auto-tiling; kinematic character controller; camera component; sprite animation state machines with frame events; tweens; emitter pools; materials with hot reload; semantic frames and annotated screenshots; obs.diff, obs.trace, obs.why.

GateSwarm and Delve are playable by a human in a window. The agent builds a three-room slice of Hollow with tiles, a kinematic player, one-way platforms, and a following camera, screenshots it, describes what's on screen from the semantic frame, and fixes a visual bug it found that way. The player has a run, jump, and land animation with a footstep event that fires a sound.

Phase 2~6 weeks

Snapshot ring with age thinning, input log, sim.seek, sim.fork; marks with clip export; tuning log for tune fields; proposals; locks, undo, and the change feed; replay export in the test runner; post stack with the hit-flash and shake passes; argus mcp; argus docs --for-agent; first argus build for desktop and web so a playtest link exists before the editor does.

GateA human plays Hollow, drops three marks with notes ("dash feels late"), walks away. The agent reproduces each from replay, fixes two, and files a proposal for the third. The human returns, A/B toggles the proposal by feel, and commits it. No screen sharing, no "what were you doing". A second human opens the web build from a link and drops a mark that reaches the agent the same way.

Phase 3~8 weeks

UI tree with layout and text; dialogue and string tables; timelines; navigation grid, A*, flow fields; job system; save games with migrations; room streaming and transitions at scale; audio buses, ducking, and the adaptive music system; mod pack loading.

GateThe agent builds a headless Outpost core — colonists, needs, jobs, stockpiles, a day-night cycle — and a menu-driven in-game inspector for it, then passes the 30-day, 20-seed starvation scenario. A save from the first week of the phase still loads at the end of it, through at least one migration. Hollow reaches 200 rooms with the §17 open and stream-in numbers green.

Phase 4~8 weeks

egui editor: hierarchy, inspector with override provenance, viewport, tilemap painting, animator and timeline editors, replay scrubber, tuning panel, profiler view, agent panel, "show as command". Built exclusively on the protocol.

GateEverything the editor does appears in the change feed as a command the agent could have issued. A human tunes Outpost's food economy at 10× with sliders; the agent sees the slider path as data, sweeps the candidates, and reports which ones starve.

Phase 5ongoing

Rust plugin crates with dylib hot reload; parallel stage scheduling; 2D lighting; optional rigid-body module; skeletal 2D module; platform plugin with the Steam implementation; bounded release recorder with player bug reports; accessibility pass; every §17 target met and gated in CI; Aseprite and Tiled importers; browser editor spike; cross-platform determinism spike.

GateAll four reference games ship as example projects, each with its test suite green in CI on the reference laptop, and an agent given any one of them can add a feature end to end without reading engine source.

§19Non-goals, risks, open questions

Non-goals for v1

3D rendering and physics. Networking and multiplayer (preserved as an option by the sim-stage rule in §15, not built). Cross-platform bit-determinism. Console and mobile platforms. A visual scripting language. An asset store. Any attempt to make the agent good at aesthetic judgement — that is what §10 is for.

Two things that were candidates for this list and are deliberately not on it: modding, which §15 decides to support from the start because the architecture already is one, and the web target, which is in v1 because a shareable build is the cheapest way to get a human's feel onto the agent's work.

Risks

Rust compile times on the plugin path. The mitigation is architectural: most game logic is Luau, and the Rust path is reserved for a handful of hot systems that change rarely. If teams push more into Rust than expected, the agent loop degrades toward what it is in Bevy today.

Luau performance ceiling. Swarm's per-entity rules and Outpost's per-colonist decision logic can both get heavy. The scheduler's write-set declarations make it possible to promote a Luau system to Rust without changing anything around it, but that is a migration, not a switch.

Generality as scope. Four reference games is the honest way to test generality and it is also roughly a third more engine than one game would need: UI, dialogue, jobs, save migrations, and streaming all exist because of Delve, Hollow, and Outpost. The mitigation is that they are ordinary systems on the same protocol, not separate frameworks, and that each one has a named customer so nothing is built speculatively. The risk is the phase-3 gate slipping; if it does, ship Swarm, Delve, and Hollow and let Outpost define the next release rather than diluting all four.

Feel systems are the largest surface. §13 alone — animation, tweens, timelines, particles, post, materials, music — is more code than the ECS and the protocol together, and it is the part where a half-built version reads as an amateur engine. The mitigation is that each piece is data over the same protocol and none of it blocks phase 0; the risk is a phase-1 gate that quietly drops the animation events, at which point §10 has nothing to tune.

Long-run float drift. Outpost sessions run for hours on f32. Same-platform determinism holds, but replays from an eight-hour-old mark take minutes to reconstruct from the thinned ring, and any nondeterminism bug compounds over that window. The counter is the seed-sweep harness catching drift early, and thinning parameters that keep the worst-case replay bounded.

Editor debt. An editor built only on the protocol will lag a native one in polish for a long time. The bet is that phase-2 collaboration features are worth more to this audience than inspector polish, and that "show as command" builds a shared language that pays back.

Legibility bias. An engine optimized for what agents can see nudges games toward what agents can see. §10 is the counterweight, but it only works if the human actually plays. Teams that let the agent run unattended for weeks will get a game that passes its tests and feels like nothing.

Scope. This document describes roughly a year of work for a small team before it is pleasant. Phase 0 alone is the honest test of the thesis and should be treated as a go/no-go — and it is deliberately two games, not one, so that the go/no-go is about the protocol and not about one genre.

Open questions

  • TOML or KDL for authored files (§4). Leaning TOML for prior strength.
  • Should the snapshot include the Luau heap, or should Luau systems be forbidden any per-system state at all? Timelines (§13) take sequencing and dialogue out of the heap, which removes the main argument for keeping it; leaning toward the stricter rule.
  • Mixed clocks (§6): is "a system group binds to a clock" enough, or do tactics-style games need an explicit state machine that hands control between clocks? Decide with a small tactics prototype after phase 0.
  • Save migrations as Luau functions per component versus a declarative rename/default/drop table. The table covers most cases and is inspectable; the function covers the rest. Probably both, table first.
  • Review requests over a phone during a couch playtest: worth a small web client early, or does that wait for the browser editor?
  • Whether the C# path is ever worth it (§7).
