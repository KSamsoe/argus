# Phase 2 checklist

Section 18 of the design document lists phase 2 as one sentence and a gate. This file breaks the sentence into pieces, attaches every constraint from elsewhere in the document that each piece has to meet, and records status, the way `phase1-checklist.md` did for phase 1. The order was agreed with Kevin on 2026-09-23.

Phase 2 sentence: *Snapshot ring with age thinning, input log, sim.seek, sim.fork; marks with clip export; tuning log for tune fields; proposals; locks, undo, and the change feed; replay export in the test runner; post stack with the hit-flash and shake passes; argus mcp; argus docs --for-agent; first argus build for desktop and web so a playtest link exists before the editor does.*

Gate: *A human plays Hollow, drops three marks with notes ("dash feels late"), walks away. The agent reproduces each from replay, fixes two, and files a proposal for the third. The human returns, A/B toggles the proposal by feel, and commits it. No screen sharing, no "what were you doing". A second human opens the web build from a link and drops a mark that reaches the agent the same way.*

Already built in phase 0, and extended here rather than given items of their own: the input log (`input.record`, `input.log.get`, replay; phase 0 item 7), and locks, per-author undo, and the change feed (`edit.lock`, `edit.undo`, `edit.feed`; phase 0 item 4). Items 4 and 5 exercise them.

Decided with Kevin: the web build and the marks it sends are hosted on klab.

## 0. Seek and fork

**Status: done** (2026-09-23) in the daemon (`ring.rs`: keyframes, thinning, the budget; `sim.seek`, `sim.snapshot`, `sim.fork`, barriers, the log and history cut back on a seek, `fork` on any method), `argus-input` (the command journal, snapshot and restore, branching, `fork_copy`), `argus-sim` (`on_tick_end`, quiet ticks, switched-off systems in `SimState`), `argus-scene` (`StreamState`), `argus-audio` (variations seeded by frame, `silence`), `argus-render` (`forget_motion`), and `argus.toml` (`[ring] every`, `budget_mb`). A seek on Hollow rebuilds the hero's position to the last digit and stepping on replays the fall into the pit exactly; a fork from a past frame replays the same inputs into the same world; a fork after a script edit runs the new code beside the old. Measured in release on Swarm's arena: five minutes of play is 304 keyframes and 22.6 MB, and the worst seek in the last five minutes is 45 ms (the §17 row is 500); a keyframe of the 50,000-entity stress scene is 1.6 ms. `run.toml` carries `code`. The Luau heap question is decided the strict way, and a system that keeps state anyway shows as `diverged` on a seek. Traces: rows in the daemon's, `argus-input`'s, `argus-sim`'s, `argus-luau`'s, `argus-ecs`'s, `argus-audio`'s, and `argus-render`'s. Found while building it: the input log alone replays a toggle wrong, so commands are journaled; a live command after a seek back branches the run even when no recorded command waits; and the audio's variation stream had to be seeded by frame for `sound.played` to replay. Constraints:

- §6: a run is a value. Given the same scene, seed, input log, and code version, the world at tick N is bit-identical. Seek, fork, marks, and tests work identically on the continuous and the discrete clock.
- §6: a snapshot is every SoA column plus the RNG states, the event queue, and the Luau heap. Phase 0 built `SimSnapshot` (the world plus clocks, seed, RNG states, and play state); what lives outside the world is not in it yet: the input state, the particle pools, which rooms are loaded, and which systems a fault switched off.
- §6: in development the daemon keeps a ring of keyframe snapshots (every 60 frames by default, configurable) plus the full input log; `sim.seek {frame}` restores the nearest earlier keyframe and replays inputs forward.
- §6: the ring thins with age (every second for the last minute, every minute for the last hour, every ten minutes beyond), so a mark from three hours ago still reproduces, with a longer replay.
- §17: a full snapshot at 100k entities under 5 ms ("keyframes every second must be invisible during play"); seek to any point in the last 5 minutes under 500 ms ("marks and A/B toggling must feel instant").
- §6: `sim.fork` creates a second world from a snapshot inside the same daemon; forks get their own tick counter and step independently. It is how the harness runs "same inputs, two code versions" and how A/B toggling works (§10, item 4).
- §5: the `sim` namespace has `seek`, `snapshot`, and `fork` (`save` and `load` are save games, phase 3).
- §6: the recorder stores a run's identity as `{scene, seed, code, clock, inputs}`; `code` (the git revision, `+dirty` when edited) is carried in from phase 0.
- §19 open question: include the Luau heap, or forbid Luau systems any per-system state. The design leans to the stricter rule, and phase 0 made globals read-only.

Decisions taken while planning it, confirmed in the build:

- **The ring keeps one keyframe a second for the last five minutes, not the last minute.** §6's schedule and §17's seek target disagree: with one keyframe a minute from the second minute on, a seek four minutes back replays up to 3,600 ticks, and §17's own fast-forward gate (2,000 ticks a second) makes that 1.8 s. Beyond five minutes the schedule is §6's. A byte budget thins further when snapshots are large; the run's first keyframe is always kept, so any frame stays reachable.
- **Inputs are journaled as commands.** The phase-0 log records the value each action ended at, which replays a toggle wrong (a recorded release flips it again) and cannot rebuild the input state between keyframes (the releases an inject schedules for itself). The input state keeps a journal of the commands it was given, each stamped with the tick it came before; a keyframe holds the input state, and a seek re-issues the journal from there. The value log stays the recorded, replayable artifact of phase 0.
- **After a seek, the recorded future plays on until someone acts.** Stepping after `sim.seek` replays what happened next; a new command (an inject, a key) branches the run, and the recorded future after that tick is dropped.
- **Out-of-band changes take a keyframe.** An edit commit, an undo, a room transition, or a script reload changes the world between ticks and is not an input, so a replay across it would miss it. A keyframe right after each one means a replay never crosses one.
- **Seek rewinds the simulation, not authored files.** Edits written to files stay; undo is the tool for those.

## 1. Web spike

**Status: done** (2026-09-24). Findings, numbers, and how to run it are in `web-spike.md`. Hollow's player runtime runs in Chrome from a pack, draws with WebGPU (WebGL2 forced runs on ANGLE, same picture), plays its sounds through Web Audio, and takes keys from the canvas. Browser and desktop runs agree bit for bit: the world and event digests of Hollow's run scenario match at every checkpoint, across a release build, a size-tuned build, and wasm under Node. So a web mark is the run's identity plus its input log and two digests (239 bytes), and the desktop replays it from load to the same world; §6's fallback (replaying web marks in the web build run headless) is not needed for Hollow. Built for it: `argus-os` (every file and clock access of the eight runtime crates, an in-memory file system in the browser), `argus-web` (packs, a daemon-less `Player`, the page's bindings, the `mark_replay` example), `Renderer::web`, argus-audio's device over cpal's Web Audio backend, and `tools/web/` (build, serve, and a headless Chrome check that replays its own mark natively). The wasm module is 8.3 MB as built and 4.25 MB tuned for size (1.5 MB gzipped); a tick of Hollow is 0.04 ms in Chrome. Found while building it: the planks test was writing Hollow's `player.toml` through `edit.commit` (the gate commit carried the hero under the plank), so `test.run` now edits the live world only; and the first frame showed the camera before it settled, so the camera also runs at load. Traces: `argus-os`'s and `argus-web`'s, and rows in `argus-render`'s, `argus-audio`'s, `argus-camera`'s, and `argus-test`'s. Constraints:

- §15: the web target is wasm + WebGPU with a WebGL2 fallback, from the start, "how most 2D games get playtested".
- §15: nothing in the player runtime listens on any socket; the protocol is compiled out of release builds as a Cargo feature.
- §6: cross-platform bit-determinism is a non-goal. The spike measures whether Hollow's run from the same inputs matches between the browser and the desktop; if not, web marks are replayed by the web build run headless.
- Questions it answers: Luau (C++) in wasm through mlua, wgpu's WebGPU and WebGL2 backends with the renderer as it is, audio through the browser, the input path from a canvas, and what a mark from the browser can carry and send.

## 2. Marks and clips

**Status: done** (2026-09-24) in the daemon (`marks.rs`: `mark.drop`, `mark.list`, `mark.get`, `mark.open`, `mark.note`, `mark.close`, `mark.import`, the F8 prompt; `replay.rs`: replay files), `argus-ecs` (a world to bytes and back, `World::digest`), `argus-sim`, `argus-input`, `argus-particles`, and `argus-scene` (their parts of a keyframe to bytes and back), and `argus-render` (the overlay bar, typed text from the window, animated PNGs, contact sheets, offscreen renderers that change size). F8 in the window drops a mark at that frame, pauses, and asks for a note on the window's bottom line; Enter keeps it, Escape skips it, and closing the window keeps what was typed. A mark is a directory in `.argus/marks/`: the note, the run's identity, the world's digest, the last five seconds of input and events, the frame, a two-second clip (an animated PNG and a contact sheet of eight of its pictures), the last two seconds of sound, and a replay file that reproduces it in a daemon that did not take it. `mark.open` plays the five seconds before the mark into the event log and the traces and compares the world with the saved one field by field; after a code change the difference is the change's effect at that frame. A mark from the web build goes into the same queue with `mark.import`, and a test shows the daemon reaching the browser's world exactly. A mark on Hollow takes 0.37 s in a debug build with the window open (the clip is 0.32 s of it), and its files are 13 KB of replay, 75 KB of frame, 1.7 MB of clip, and 384 KB of sound. Found while building it: the offscreen renderer was rebuilt whenever a size changed (now it changes the size of its texture), the PNG crates are several times slower unoptimized (they are optimized in debug builds now), and winit's one event loop a process means the window tests are one test. Traces: rows in the daemon's, `argus-ecs`'s, `argus-sim`'s, `argus-input`'s, `argus-particles`'s, `argus-scene`'s, and `argus-render`'s. Constraints:

- §10: while playing, the human presses one key (F8 by default) to drop a mark. A mark captures the frame, a snapshot, the last five seconds of input, a two-second clip rendered from the ring, and an optional one-line note typed afterward ("dash feels late").
- §10: marks land in `.argus/marks/` and surface to the agent as a queue; each is a fully reproducible bug report. The agent runs `sim.seek` to the mark's frame, traces the relevant entities, and proposes a change without asking "what were you doing".
- §16: `marks` is one of the MCP tools.
- The clip is rendered offscreen from replay (seek to two seconds before, step, capture), so marks need no GPU frame ring and work headless.
- The note is typed in the window before the UI tree exists (phase 3): one line drawn with the annotation font from phase 1 item 12.

The first playtest (Kevin, 2026-09-24) dropped three marks on Hollow. Two were a sign ("what is this thing?", "another one here"): opened, each was `@b/sign` or `@c/sign`, whose words ("Mind the pit.") reached the agent through the semantic frame and never the player; the HUD line was never drawn either. Fixed with `Describe.shown` (the renderer draws a game's own text in the pixel font until phase 3's UI tree), a signpost sprite with its board above the hero's head, and a Hollow system that shows a sign's words while the hero is near. Reopened after the fix, each mark's only difference at its frame was its sign's `Describe.shown`, false to true, and both were closed with that note. The third mark had no note and is open.

Decisions taken while building it:

- **A mark is files, and it outlives the daemon.** Closing the game's window ends the daemon, so a mark kept in memory would be gone by the time the agent looks. The replay file holds a keyframe (the world, the clocks and random streams, the input state, the particle pools, the rooms), the input commands after it, and the world at the mark. The same file serves item 3 (a failing test's replay) and item 7 (a release build's report key).
- **"A snapshot" is two.** The keyframe the five seconds before the mark start from, so opening the mark rebuilds those seconds for `obs.events` and `obs.trace`; and the world at the mark, so opening it after a fix says field by field what the fix changed there.
- **A saved world reads into newer code.** Components are matched by name; a component whose fields changed is copied field by field, new fields taking their defaults; one that is gone is dropped and named. Strings are translated into the reading world's table. The alternative, refusing a mark once any schema changes, would make marks useless exactly when the agent is fixing what they show.
- **The clip is for the human; the agent also gets a contact sheet.** An agent reading an animated PNG sees its first picture only, so eight of the clip's pictures, labelled with their frames, go into one picture beside it.
- **Notes are typed, not spoken.** §10 says "spoken or typed"; speech needs the microphone and speech to text, which is not this item.
- **The key is F8 unless the project says otherwise** (`[marks] key` in `argus.toml`, by the name the window sends: `Backquote`, `KeyM`). F9 stays free for item 4's A/B toggle.

## 3. Replay export in the test runner

**Status: done** (2026-09-24) in `argus-test` (the harness saves a failing run's replay the moment it fails) and the daemon (`replay.save`, `replay.open`; marks are built on the same capture). A run's first failed expectation, or its error, saves `.argus/replays/<scenario>/seed<n>/`: the replay file, the frame, a clip of the two seconds before and its contact sheet, the sound, and `replay.json` with the failure's message and the scenario, file, and seed. `argus test` prints `replay at frame N: argus replay open path=...` under the failure, and `replay.open` reproduces it paused at that frame, the lead-in in the log and the traces, so `sim.seek` and an open window work on it until the editor (phase 4). The first five failures of a run get clips; `--software` draws them with the software rasteriser, as CI would; `--no-replays` saves none. On Hollow a deliberately failing scenario saved both of its seeds at the failing frame (120, not the run's end at 180), and the replay reopened to the same world. Traces: rows in `argus-test`'s and the daemon's. Constraints:

- §9: run a failing test and dump a replay file the human can open (in the editor, phase 4; with `sim.seek` until then), and export a short clip of the failing window so the human can see it without reproducing it.
- §9: everything runs identically in CI with the software render adapter.

Decisions taken while building it:

- **The replay is of the moment it failed.** The harness saves when the first expectation fails (or the script errors), not when the run ends; a run goes on after a failed expectation, and its end can be far from what went wrong.
- **A mark and a replay are one thing.** `replay.save` is a mark without the queue, and a mark is a replay with a note and a place in the queue; the item 7 report key will write the same.
- **Clips are capped, replays are not.** A seed sweep that fails on all fifty seeds keeps fifty replay files (a few kilobytes each) and five clips.

## 4. Proposals and A/B by feel

**Status: done** (2026-09-24) in the daemon (`proposals.rs`: `edit.propose`, `proposal.list`, `get`, `try`, `show`, `pick`, `reject`, `stop`, F9 and F10 in the window; the feed's `proposed` and `rejected` rows) and `argus-input` (a journal another world's commands join; due commands issued when a world is switched to). The agent proposes a transaction instead of committing it; more transactions into the same proposal are its variants B, C, and so on. Proposals are files in `.argus/proposals/`, so one made while the human is away waits for the game they come back to. In the window F9 tries the oldest waiting proposal: each variant becomes a fork of the world at that moment with its edits applied, and every world then takes the same input at the same tick, the ones not showing catching up behind the one that is, silently, every frame. F9 goes round A, B, C; the bottom line says which world shows and what it changes. F10 keeps the world showing: a variant is committed as an ordinary commit by the one who picked, which the feed shows and undo takes back, and the game goes on in that world; keeping A turns the proposal down. On a copy of Hollow, proposing jump heights 3.8 and 4.4 against 3.2 and jumping once in A put the hero at heights 3.71, 4.07, and 4.44 at the same tick 40 in A, B, and C. Found while building it: building a fork cleared the session's change feed, undo stacks, open transactions, and locks (an item 0 bug, fixed), and dropped the offscreen renderer. Traces: rows in the daemon's and `argus-input`'s. Constraints:

- §10: the agent can submit a transaction as a proposal rather than a commit. The human plays with F9 toggling between the current world and a fork with the proposal applied, at the same replay point, with the same inputs. Several variants become several forks and one key cycles them. The pick is the commit; nothing requires the human to read a diff.
- §10: the human can lock any entity, component, or path; the agent's write fails with the owner's name and note. Both parties see one author-tagged change feed. (Phase 0 built these; proposals join the feed.)
- §16: `propose` is one of the MCP tools.
- Before the editor (phase 4), pending proposals are listed through the protocol and toggled in the game window.

Decisions taken while building it:

- **"The same replay point, with the same inputs" is worlds kept in step.** The forks start from the world as it is when F9 is first pressed, and from then on every world gets the input the one showing gets, at the same tick: the others take its new input commands as their recorded future and catch up behind it every frame. Switching is instant and lands at the same moment. Rewinding to a point instead would make the human replay what they just did, and playing by feel means playing on.
- **F10 keeps.** §10 names F9 for switching and says the pick is the commit; F10 is the key for it. winit gives F10 to the game, not to Windows' menu, since the window has no menu. F9 and F10 are fixed for now; F8 is `[marks] key`.
- **The pick is committed by whoever picks.** Their own locks do not stand in the way, and a proposal may touch what the human locked: a lock stops the agent writing, and proposing is how the agent asks. Another author's lock still refuses the pick.
- **The game goes on in the picked world** when its edits are field writes (set, add, remove); a variant that spawns or despawns is committed in A and the game goes on there, since entity handles differ between worlds.
- **A seek or a scene load ends a trial**; the worlds keep step going forward only.
- **Previews change memory only.** A variant is applied to its fork without writing files and without locks; a spawn with an id (which would be a file) cannot be previewed and is refused when proposed.

## 5. Tuning log

**Status: done** (2026-09-24) in the daemon (`tuning.rs`: `tune.fields`, `tune.begin`, `tune.set`, `tune.end`, `tune.log`, the `tune` subscription topic, and every commit's tune fields logged). Every change to a tune field goes into `.argus/tuning.jsonl` with its frame, author, value before and after, and how it came: `tune.set` (the slider, until the editor has one), an `edit.set` commit, a picked proposal, undo, or redo. `tune.log` gives the rows and each field's search path in one line, as §10 writes it: "human set @a/player CharacterController.jump_height 3.2→3.6 at frame 60, →3.4 at frame 120, →3.5 at frame 180". `obs.subscribe {topics: ["tune"]}` streams each row as it is written. `tune.set` changes the live game only and belongs to a tuning session; `tune.end` commits the session's final values as one transaction by its author, whose undo goes back to where the session started. Closing the game's window, or loading a scene, ends a session and commits it. A proposal's check, a trial's previews, and a test's edits change no one's tuning and are not logged. Traces: rows in the daemon's and `argus-ecs`'s. Constraints:

- §3, §10: a field with `tune = true` is logged by the recorder whenever it changes, with its frame: "human set HitStop.scale 0.0→0.15 at frame 3011, →0.08 at 3090, →0.1 at 3140". The agent subscribes to the stream and sees the search path, not only the final value.
- §10: when the human ends a session, the final values are committed as one transaction with the human as author.
- The slider panel is the editor's (phase 4). Until then tune fields change through `edit.set` and proposals, and the log records those.

Decisions taken while building it:

- **`tune.set` is the slider until there is one.** It changes the live world and not the files, so a human can move a value many times while playing (from a terminal beside the game, `argus tune set ...`), and only the end is committed. `edit.set` stays a commit, logged as one.
- **A session's commit is one transaction whose undo goes to the start.** Before committing, the session's fields are put back to where it found them, so the transaction's inverse is the value before the session, not the last slider move.
- **Closing the window commits.** Closing the game is how a human ends a session without the editor; losing the tuning would be worse than keeping a value they can undo. A scene load commits first too, since it would lose the live values.
- **The log is a file,** as marks and proposals are: the human tunes, closes the game, and the agent reads the log in another daemon.

## 6. Post stack

**Status: done** (2026-09-24) in `argus-post` (the components `PostShake`, `PostFlash`, `PostFade`, `PostVignette`, `PostAberration`, `PostPalette`, and `PostHitStop`, and the systems `post.hitstop` and `post.update`), `argus-render` (`post.rs`: the passes, drawn between two textures after the world; the effects in the semantic frame), `argus-sim` (`SystemCtx::freeze`, `unfrozen` and `first` systems), `argus-luau` (`unfrozen = true`), `argus-camera` (a stop holds the view and the shake plays on), `argus-physics` (a tap inside one tick still jumps), and `argus-index` (exact floats). A game turns passes on with components on its camera, each setting a tune field, and the renderer runs the ones doing something in `order`. The flash, the shake, and the hit-stop each start on a game event by name (`hit` by default; an `amount` on the event scales the flash and the shake), so one event starts all three and one tuning session adjusts them together. Hollow's fall into the pit is the example: a red flash, a screen shake, and a six-tick stop, with the view held on the pit while the flash and shake play. A script fades a room change with `PostFade`. Measured: five passes at 1080p cost 0.164 ms on the RTX 3070 Ti (the §17 row is 1.5 ms). Found while building it: the design's own example of a game component is called `HitStop`, and the engine's took that name and broke a test project that declared one, so the engine's is `PostHitStop`; letting the camera run through a stop also let it pan away from the hit, so it now holds; a tap made during a stop arrived as a press and a release on the same tick, which the controller missed; and the index read floats back one step off in the last bit, which the new shake default was the first to show. Traces: `crates/argus-post/SPEC-TRACE.md`, and rows in `argus-render`'s, `argus-sim`'s, `argus-luau`'s, `argus-camera`'s, `argus-physics`'s, `argus-index`'s, `argus-web`'s, and the daemon's. Constraints:

- §13: screen-space effects live in a post stack, an ordered list of passes (flash, palette swap, chromatic aberration, vignette, CRT, colour-blind simulation) a game enables with parameters, every one a tune field. Phase 2 builds the stack and the hit-flash and shake passes.
- §13: the hit-flash, hit-stop, and shake combination that makes an impact feel heavy is three tunable systems the human adjusts together in one session.
- Carried from phase 1: the camera's shake is in world space; screen-space shake is this pass. Fades for room transitions are post passes too.
- Semantic frames (§8) report active post effects, as they report the camera's shake.

Decisions taken while building it:

- **A hit-stop freezes the tick, not the clock.** The tick still counts, so input, replays, marks, and the clocks stay on their ticks; the systems not marked `unfrozen` skip it. The design's §3 example does it per entity through a time scale; the trio needs the whole game to stop while its effects play, so the engine's stop is global and a game that wants one entity frozen writes its own component, as §3 does.
- **Input waits through a stop.** The input system is frozen with the game, so what was pressed during a stop is applied on the first tick after it. A press and its release can then land together, and the controller counts that as a jump (a short one).
- **The camera holds its view during a stop and shakes on.** A camera that went on following would slide away from the moment the stop is there to show.
- **Screen shake is a share of the screen's height**, so it looks the same at any window size; the camera's shake stays in world units and moves the view.
- **The passes are components on the camera**, not a list in `argus.toml`: they are tuned, logged, proposed, and replayed like any field, and a room or a cutscene can change them.
- **CRT and the colour-blind simulation are deferred.** The item scopes the stack plus the flash and shake passes, and §17's row names five passes, all built. Both are one more fragment function on this stack; the colour-blind pass belongs with the accessibility work.
- **Room fades are a script's tween.** `camera.zone` is the hook; a script ordered after the camera sees it on its tick. Hollow keeps its camera slide.

## 7. argus build, desktop and web

**Status: done** (2026-09-24), macOS deferred (there is no Mac here). `argus build` makes a release of a project for Windows or the web, and a Linux or macOS release on those platforms (Linux built on klab); `argus-player` holds the runtime every build and the daemon share; `argus-game` is the release executable. A release is one directory: the executable named for the game (it links no protocol, index, or daemon, and has none of the protocol's strings), and `data/` with a content-addressed game pack, a patch pack per later build made with `--since`, and a pack per language (`lang/<code>/`). Packs come from the import cache (each sprite's cached texture and what the importer made of it; the source art stays home) with the scripts compiled to Luau bytecode; the executable mounts them in memory, so it writes nothing but its save location. The bounded recorder keeps two keyframes 30 seconds apart and the input since the older; F8 (or `[marks] key`) in the executable saves a report, a replay file of the last 30 to 60 seconds with the player's note, and a crash saves one too; the web page's F8 posts it to the server it came from (`tools/web/serve.mjs`), and `argus mark pull` imports those as marks, which `mark.open` reproduces. Every build checks itself: the game from its packs, and the executable run headless, reach the project's world after 300 ticks. Measured on Hollow: the game pack is 35 KB (32 files), the release executable 15.8 MB, a release build of it took 58 s, and a report is 15 KB. In Chrome the pit's report went through the server and replayed natively to the same world. On klab (2026-09-24): the Linux release built in 1 min 20 s (13.6 MB) and reaches the same world after 300 ticks as the Windows one, bit for bit; the page runs as `argus-play.service` (docs/playtest.md), and a report posted to it was pulled over an SSH tunnel and opened as a mark that reached the same world. The playtest link is `https://klab.tailde2255.ts.net:8443/` (tailnet only, Let's Encrypt certificate through `tailscale serve`); a report posted over it was stored and listed. The phase 2 gate, a second person playing it and dropping a mark, is next to the gate itself. Found while building it: the web player's copy of the daemon's assembly had drifted (it ignored a scene's system groups), the index's floats were fixed in item 6, `write!` on a raw socket sent a request in pieces, and the workspace's debug build caches had filled the disk (27 GB of incremental data, cleared). Traces: `crates/argus-player/SPEC-TRACE.md`, `crates/argus-game/SPEC-TRACE.md`, and item 7 sections in the daemon's, `argus-cli`'s, `argus-web`'s, `argus-luau`'s, `argus-assets`'s, `argus-os`'s, and `argus-input`'s. Constraints:

- §15: a release build is the same core with the protocol server compiled out, the editor and index absent, Luau precompiled to bytecode, and assets packed; no socket, no `.argus/`, no way to attach. The dev surface is a Cargo feature, not a runtime flag.
- §15: `argus build --release --target windows` produces one directory: the executable, one asset pack per language, and a save location per platform convention.
- §15: the recorder stays in release, bounded: the last thirty seconds of actions and a keyframe, so a report key or a crash produces a replay file `sim.seek` can open. A player bug report becomes a mark.

Decisions taken while building it:

- **One assembly, in a crate of its own.** The daemon, the web page, and the executable build a scene's world with `argus_player::assemble`, so "the same core" is one function, not three copies kept in step. Keyframes and replay files moved beside it, since the recorder needs them and the daemon must not be linked.
- **The dev surface is a crate the release does not link**, stronger than a feature: nothing in the shipped executable can be switched on to reach a protocol.
- **Packs are built from the import cache for sprites, from sidecars for the rest.** A sprite's cached texture and its catalog entry replace the source image and sidecar; sounds, animators, emitters, and materials are small text and import at start in milliseconds. Atlases, texture compression, audio codecs, and binary scenes wait until a game's size asks for them; Hollow's whole game pack is 35 KB.
- **Blobs are addressed by SHA-256.** A weaker hash could make a patch ship the wrong file without anyone noticing; SHA-256 is small enough to write and check against the standard vectors, so no new dependency.
- **A language pack lays whole files over the game's.** String tables belong to the UI tree (phase 3); until then a language replaces the files that hold text.
- **The recorder keeps two keyframes 30 seconds apart**, so a report reaches back 30 to 60 seconds and memory stays bounded however long the game runs. A report is the same replay file as a mark's, so the daemon opens it the same way.
- **A report is posted to the server the page came from.** The playtest server is `tools/web/serve.mjs`; `mark.pull` fetches from its LAN or tailnet address over plain HTTP. A desktop report is saved in the save location for the player to send.
- **A desktop build is made on its own platform.** The executable links the platform's window, audio, and gamepad libraries, which a cross-compile from Windows cannot reach; `argus build --target linux` says so rather than half-working.
- **`argus build` is a local command**, like `daemon`: a release takes minutes of cargo and needs no running game. It builds the executable from the engine's source tree; a packaged engine would ship them prebuilt.
- **The playtest server listens on klab's localhost and tailnet address only**, never the home network: Tailscale's HTTPS proxy gives players the page, and `mark.pull` reaches the tailnet address (or an SSH tunnel, from a machine off the tailnet).
- **The executable was checked headless.** Its report key and window were not driven on Kevin's desktop; `--headless` runs the same game with no window, which is how the build checks itself.
